1. Objective

Verify that the VWO login experience gives returning and new users a reliable entry point to the experimentation platform. Testing will check the authentication and recovery journeys, input validation, user feedback, responsive behavior, accessibility, integrations, and the security and performance requirements stated in the PRD.

Testing will also assess the specified success measures: login success rate of at least 95%, login-page load time under 2 seconds on standard connections, and user satisfaction of at least 90%. System availability, security, compliance, and support-volume measures require appropriate operational or post-release evidence in addition to functional testing.

2. Scope

In scope

  • Email/password login, field validation, authentication outcomes, loading and success states.
  • Remember Me and secure session behavior, including configured timeout and return to the VWO dashboard.
  • Forgot-password and email-based recovery, password requirements, and recovery feedback.
  • Optional 2FA and enterprise SSO flows (including SAML/OAuth) where enabled in the test environment.
  • Login and failure analytics, support assistance paths, registration/free-trial link, and product announcement/theme options.
  • Responsive layout, keyboard and screen-reader access, high contrast, and light/dark themes.
  • Transport and session security, rate limiting, privacy/data-handling requirements, and performance targets.

Conditional or not in scope

  • Social login is optional in the PRD; test it only if selected for this release and configured.
  • Biometric authentication, adaptive authentication, and Progressive Web App enhancements are future enhancements and are not included in this release plan.
  • Full platform-wide availability, multi-region failover, and concurrent-user capacity are assessed with operational/performance plans and service evidence; login-focused checks are included here.

4. Test Environments

  • Environment URLs: QA and pre-production URLs are TBD. The PRD identifies app.vwo.com/login as the login entry point; execution should use an approved non-production target unless production testing is explicitly authorized.
  • Desktop: Windows, macOS, and Linux; current supported Chrome, Firefox, Edge, and Safari versions to be confirmed.
  • Mobile: Android with Chrome and iOS with Safari; supported OS/browser versions and representative device sizes to be confirmed.
  • Responsive coverage: Desktop, tablet, and smartphone viewport sizes, including portrait and landscape where supported.
  • Network: Standard connection for the 2-second page-load target, plus agreed slower and variable network profiles for resilience checks.
  • Accounts and integrations: Synthetic accounts for valid, invalid, locked/throttled, recovery, 2FA, and SSO scenarios; identity-provider setup and roles TBD.
  • Access: Test environment credentials, permissions, and audit access must be provisioned through approved channels before execution.

5. Defect Reporting Procedure

  1. Record each issue in the designated Jira project (project/key TBD) with a concise title, environment/build, preconditions, reproducible steps, expected and actual results, and reproducibility.
  2. Attach only relevant screenshots, sanitized logs, and test evidence. Do not include real user credentials, personal information, or secrets.
  3. Assign severity and priority using the project’s agreed definitions; route authentication, privacy, accessibility, and availability defects to the appropriate triage owner (TBD).
  4. Review new and reopened issues during triage. Retest the fix in the target environment and run relevant regression coverage before closure.
  5. Share execution and defect status with stakeholders through the agreed project channel and reporting cadence (TBD).

6. Test Strategy

  1. Requirement analysis: Map each PRD requirement to scenarios and clarify unspecified behavior, supported versions, error copy, session policies, password rules, and measurable load profiles.
  2. Test design: Apply equivalence partitioning and boundary-value analysis to input validation; decision tables to login configuration and account states; state-transition testing to authentication, session, and recovery; and use-case testing to end-to-end user journeys. Use exploratory testing for usability and edge cases.
  3. Smoke and sanity: On each candidate build, verify the page loads, core fields are usable, login and recovery entry points respond, and no blocking issue prevents deeper testing. A failed smoke check blocks the full cycle pending a stable build.
  4. Functional and integration testing: Execute prioritized scenarios for login, reset, session behavior, 2FA/SSO when enabled, dashboard transition, analytics, support, registration, and themes.
  5. Non-functional testing: Cover responsive compatibility, WCAG 2.1 AA checks, performance against stated targets, security-control verification against approved requirements, and agreed concurrency testing.
  6. Regression and retesting: Retest fixes and run the affected login, session, recovery, integration, and cross-browser checks. Repeat cycles until exit criteria are met.
  7. Evidence: Maintain traceability from requirement to scenario, result, and defect. Report pass/fail/blocked status and attach sanitized evidence.

Priority focus: Authentication success/failure, recovery, session security, and access control are release-critical; validation and integration paths follow; broad compatibility, accessibility, and performance coverage proceed alongside them.

8. Test Deliverables

  • Approved test plan and requirement-to-test traceability.
  • Prioritized test scenarios and test cases, including environment and data requirements.
  • Smoke, functional, integration, compatibility, accessibility, security-control, and performance execution results.

9. Entry and Exit Criteria

Requirement analysis

Entry: PRD and available design or integration details are provided.

Exit: Requirements are reviewed; testable acceptance expectations and open questions are recorded.

Test design

Entry: Scope and requirements are available to the test team.

Exit: Prioritized scenarios, test data needs, and traceability are documented and approved by the designated reviewers.

Test execution

Entry: Approved build and environment are available; required access and synthetic accounts are ready; smoke checks pass.

Exit: Planned tests are executed or explicitly marked blocked; results and defects are recorded; critical authentication paths pass; no unresolved release-blocking defect remains; target metrics are reported against agreed measurement conditions.

Test closure

Entry: Execution results, defect status, and evidence are ready.

Exit: Test summary is delivered, outstanding items and accepted exceptions are documented, and designated stakeholders record the release decision.

10. Test Execution

  1. Confirm build, environment, feature flags, supported browser/device matrix, test accounts, and integration availability.
  2. Run the smoke checklist. If a blocking check fails, report it and pause full execution until a stable build is available.
  3. Execute prioritized cases across agreed supported environments; record actual results and attach sanitized evidence.
  4. Log defects, participate in triage, and retest fixes. Run regression checks for impacted flows.
  5. Publish status at the agreed cadence. Escalate blocked tests or unmet targets through the project’s agreed process.

PRD measures to report: authentication success rate (target ≥95%); login-page load time (target <2 seconds on standard connections); user satisfaction (target ≥90%); availability target (99.9%, measured operationally); and support-ticket reduction target (20%, measured after release). Definitions, sample windows, and data sources must be agreed before measurement. Security objectives include no successful unauthorized access and no successful brute-force attacks; validation must use authorized, controlled test conditions.

11. Test Closure

At closure, consolidate execution coverage, results by environment, defect status, deviations from scope, metric observations, and unresolved items. Confirm that required test evidence is stored in the approved project location and that release stakeholders have reviewed the summary.
